# MindAttic Agent Standard

## GOLDEN RULE: verification is build-only; tests run last, once, when the user asks

The owner, 2026-11-07: "you can't sit around idle for half an hour to run entire test suites... its such a
waste of resources to let something retest every little change 100s or 1000s of times in a 5hr period, this
needs to be a GOLDEN RULE that everything follows."

- **Verification is build-only.** Check a change by building it, then commit and move on. Never run a test
  suite, a filtered slice of one, a bot soak or a balance run to verify your own work.
- **Tests run last, once, and only when the user asks** in their own prompt: `/test` (or `/tests`, `/run
  tests`), or "run the tests". `/commit` never runs them.
- **Orchestrators and coordinators never instruct subagents to run suites or soaks.** A subagent started by
  a user's `/test` turn inherits that permission; no other subagent has it.
- **Keep every CLI busy toward 98% of its 5-hour window** with real work instead of waiting on test runs.

Enforced by `shared/hooks/test-gate.py` (MAT-T121; see "Tests run only when the user says so" below).

Start with the repository's local `AGENTS.md`, then read this shared layer and its project
protocol. Common commands are implemented once, at the global level, so every repo has them on Day
1 with no per-project setup:

- `/do`, `/quicksave`, `/quickload` — real global commands at `~/.claude/commands/` (for Claude
  Code) that invoke the shared runner, `mindattic-agent-standard/prose-agent.ps1` (`save`/`load`).
- `/quicksaves` — a real global command (source `shared/abilities/quicksaves.md`, MAT-T109, renamed
  from `/handoffs` in MAT-T113 to match `/quicksave`/`/quickload`): a brochure of every pending
  (unconsumed) handoff from `prose-agent.ps1 quicksaves -Json` — code, alias if any, repo, and a
  <=255-character plain-English description of what it's about (the registry's own `description`
  field when present, else summarized live).
- `/alias <type> <real-name> <alias>` — a real global command (source `shared/abilities/alias.md`,
  MAT-T110): attaches, replaces or clears (blank `<alias>`) a human nickname on a pending handoff
  at any time, not just at `/quicksave` time. Only `type` `handoff` exists today. Stored as a real
  `alias` field on that handoff's own registry file — `load`/`/quickload` and `/quicksaves` resolve
  or display it the same way they do the handoff's real code; nicknames stay unique among pending
  handoffs the same way codes do. `/quicksave <name>` sets this automatically after saving.
- `/commit` — global, Claude Code's own `~/.claude/commands/commit.md`.
- `/run` — global, a Claude Code built-in skill; no MindAttic-specific file needed.
- `/deploy` — global router at `~/.claude/commands/deploy.md`: defers to the repo's own
  `run.ps1` (renamed from `deploy.ps1`; its generated `run.bat` launcher asks Deploy & Run or Run), else routes through MindAttic.Deploy, else says plainly that the repo has no
  automated deploy. Per-project deploy *behavior* still varies — the router doesn't.
- `/progress` — a real global command at `~/.claude/commands/progress.md` that runs
  `mindattic-agent-standard/agent-progress.ps1`: every running subagent (any session or project),
  its ticket, what it is doing now, and an estimated percent done from its milestones (explore →
  edit → test → commit → push → ticket closed). `prose-agent.ps1 progress` runs the same report
  outside Prose; inside Prose, Prose's own project `/progress` (the strand dashboard) still wins.
- `/test` — a real global command at `~/.claude/commands/test.md` (source
  `shared/commands/test.md`): runs the current repo's entire test suite on `origin/main` in a clean
  worktree, names every failure and files a fix ticket for each. It is the explicit way to ask for
  tests (see "Tests run only when the user says so"). `/tests` is an alias (`shared/commands/tests.md`, a
  forwarder to `test.md`). **`/run tests` (or `/run test`) is an alias too:**
  when the built-in `/run` skill is invoked with `tests` or `test` as its whole argument, don't launch
  the app; follow `/test` (read `shared/commands/test.md`) instead.
- `/research <who> <what>` — a real global command (source `shared/commands/research.md`): files a
  research ticket in the current repo, starts a CLI on that member's login (`orchestrator org start
  <repo> <who> --prompt`) that answers the open questions in `<what>` (pasted text works), writes
  `docs/research/<Topic>.md`, commits it, closes the ticket, notes the related tickets and messages the
  sending session back by its ListAgents name (MAT-T89).
- `/<member> research <what>` or `/<member> <message>` — one global command per alias of every active
  org member, generated by `shared/member-commands.ps1` (run from `share-scripts.ps1`) from
  `shared/commands/member/*.template`. A member answers to their name, their initials (for names of two
  or more words) and the part of their email before the @. `research` does what `/research` does; anything
  else is a message to that member's running CLI, or opens one on their login with it. An alias
  several members share asks "Did you mean X or Y?" before doing anything. Names, initials and emails
  should stay unique (M.ORCH-T1445).
- `/show`, `/bootstrap`, `/queue` — implemented directly by the shared runner
  (`prose-agent.ps1`); invoke it by path rather than duplicating its logic.

Every command above is written once, as source, and rendered out to each CLI's own native
extension point — see "Cross-CLI capability framework" below for where each one actually lands and
what's confirmed to work versus still unverified per CLI.

## Cross-CLI capability framework (MAT-T93/94/95/96)

## Cloning a new repo

Never run a bare `git clone` into the workspace. Use
`mindattic-agent-standard/clone-repo.ps1 -Repo <owner/name or name>`, which does all four steps
every new repo needs, in order, with nothing left to remember:

- **A)** creates the destination folder, **B)** clones the repo into it,
- **C)** tags the repo `wip` on GitHub — the only lever
  `MindAttic.Launcher`'s `TopicRepoSync`/`GitHubTopicRepos` filter the project roster by; an
  untagged repo exists on disk but never shows up in the Launcher,
- **D)** restarts any open `MindAttic.Launcher` **program** instance (a bare, no-argument
  process — the interactive menu) so it re-fetches the tagged-repo set and offers the new repo
  through Discover Projects. A `host ...`/`commit ...`/`backup ...`/`restore ...`/`bootstrap
  ...`/`version` instance is a live per-tab CLI invocation, not "the program", and is left
  running untouched.

This applies whether the clone is for a brand-new repo or an existing one the workspace hasn't
picked up yet (e.g. a repo missing its `wip` topic): `clone-repo.ps1` tags and restarts even when
skipped past the clone step for a repo already on disk — see the script's own doc comment.

## Branches

**GOLDEN RULE (see `MINDATTIC_AGENT.md`): always layer code on top.** Work only in the repo's own
checkout, on `main`, on top of the latest `origin/main`. Never create a separate branch or worktree
(no `git checkout -b`, no `git worktree add`, no subagent isolation worktrees), unless the user
explicitly asks for one in that request.

Every repo's main line is `main` (Automata, MindAttic.Authentication, IdeaCms (then MindAttic.Ideas), Prose and this workspace root
repo were renamed from `master` on 2026-10-16; four archived repos, MindAttic.Bob among them, are read-only and stay as they are). Rebase onto and push to `origin/main`; never push
`master` anywhere: it would only recreate a stray branch, and the pace gate refuses it.

## Ticket intake: what may join the queue without the user

- Bugs (something that's broken or wrong): file them straight away as `open` tickets with
  `--type fix`; fixes are worked without asking.
- Anything else (a feature, a change of behaviour, a chore, tests, docs), whether the user suggested it or
  you thought of it: write the ticket, print its full text for the user, and wait for the user's yes. A
  non-fix ticket is never worked until the user approves it (`orchestrator approve <ID>`); the orchestrator,
  `/allocate` and keep-going skip it until then, and so must you.

## Every request is a ticket, filed first

**GOLDEN RULE (see `MINDATTIC_AGENT.md`): every action that writes code is aligned to a ticket.** Each request
becomes a new ticket, or is appended to the existing ticket it belongs to with `tickets ticket note <ID> "..."`,
before any code is written for it. No edit, commit or deploy without a ticket.

- Step one for every task the user gives, in any CLI, is its ticket: `tickets ticket new` (in the repo the
  work lives in; another repo's part gets its own ticket there) before reading, editing or running anything
  for it. A burst of requests gets one ticket each, filed as each arrives, not backfilled at the end: a
  crashed session then loses at most the code, never the record of what was asked. Work the user asked for
  directly counts as approved (see Commits).
- Every message the agent prints starts with the ticket it's about, ID and title, e.g.
  `**[M.ORCH-T844 — Rename the dashboard exe]**`, so the user always knows which task it comes from.

## Tests run only when the user says so

Never run a test suite (or a filtered slice of one) on your own while working: a run can take 15 minutes and
blocks everything behind it. Check work by building it. Tests run only when the user explicitly asks for them
(`/test`, or `/run tests`, runs a repo's whole suite); `/commit` does not run them (a test run per commit would mean
endless testing).

**Enforced (MAT-T121).** `shared/hooks/test-gate.py` runs on every CLI (Claude, Codex, Kimi, agy; wired by
`install-hooks.ps1`):

- `PreToolUse` refuses any shell command that runs a test runner or soak (`dotnet test`, `pytest`, `npm/yarn/pnpm
  test`, `vitest`, `jest`, `cargo test`, `ctest`, `go test`, `Invoke-Pester`, `tools/test.ps1`, Unity `-runTests`,
  soak/balance runners, ...). The list is data: `shared/hooks/test-gate-patterns.json`; a repo adds its own runners
  in `<repo>/.agent/test-gate-patterns.json` (same shape, added to the shared list).
- `UserPromptSubmit` records, per session, whether the user's latest typed prompt asks for tests (`/test`, `/tests`,
  `/run tests`, or a non-negated "run (the) tests"); the next prompt replaces it, so permission lasts one user turn.
- Subagents inherit it: their tool calls carry the parent's session, and `SubagentStart` snapshots the parent
  turn's permission for that agent, so a `/test` subagent keeps it while the user types on, and others never get it.
- It fails open: any error in the hook allows the call.

## Never ask the user to say "continue": wait out the pace yourself

Applies to every CLI, every login and every provider. Never end a turn with "say continue when
you're ready", "let me know when to resume" or anything like it because usage is high: the user
should never have to come back just to type a word. When the login is over its 5-hour pace, wait
and resume on your own:

- **Read the pace from `rl-status.json`** in the login's own Claude home (`$CLAUDE_CONFIG_DIR`,
  else `~/.claude`). Its `subagent_note` field (written by MindAttic.Orchestrator's pacer) says
  `Cooling off` or `ahead of` the 5-hour pace while the login is over it.
- **Wait on a background timer, not on the user.** Start a background poll (e.g. a background shell
  loop, Monitor with an until-condition, or a one-shot wakeup) that re-reads `subagent_note` every
  minute or two and finishes once it no longer says `Cooling off` or `ahead of`; then pick the
  work back up where it stopped, without being asked. At or past the hard 5-hour stop, schedule the
  resume for the window's reset (plus about two minutes) instead.
- **Keep each login at or under 96% of its 5-hour window.** That is the hard cutoff; the wait above
  exists so a login never runs past it.
- **Ramp subagents up gradually: 3-4 at once, then more as the note allows.** The pacer's forecast
  is rate-based, so a burst of new subagents spikes the rate and overshoots the line before the
  forecast catches it. Start a few, let `subagent_note` settle, then add more.

## Printing a status while nothing's been heard from you (MAT-T108)

When a CLI has background work still running (a subagent, a long shell/PowerShell command, a
Workflow) and the user hasn't sent a new message since it started waiting, don't just go quiet until
it's done: a return visit after a while should land on a sense of what's been happening, not a blank
wait.

- **Claude Code only, for now.** This needs the *same* session to produce new, visible output on its
  own timer with no keystroke from the user — Claude's own `ScheduleWakeup` tool genuinely does
  that (it's what `/loop` dynamic mode already relies on). The portable `schedule-wakeup` ability
  (`shared/abilities/schedule-wakeup.md`) does **not** serve this despite being the provider-agnostic
  mechanism: it re-invokes a brand-new, non-interactive process that logs to its own file, never the
  live tab anyone is actually watching (its `claude -p`/`codex exec`/`kimi -p`/`agy -p` invocation
  lines never pass a resume/session flag). `ScheduleWakeup` already has no Codex/Kimi/agy equivalent
  elsewhere in this doc (the cross-CLI framework section above) — this rule inherits that same gap
  honestly rather than faking it with the portable mechanism. Leave it Claude-only until a real
  same-session wakeup exists for the others.
- **Interval**: read `intervalMinutes` from `shared/config/idle-status.json`; default to 5 if the
  file is missing or unreadable. It's a global setting — the owner (or a CLI asked to change it on
  their behalf) just edits that number and commits; nothing else reads a copy of it.
- **While background work is outstanding and the user's gone quiet**, call `ScheduleWakeup` for the
  interval. Each time it fires, check both conditions again:
  - Background work is still running, **and** the user still hasn't sent anything new since the last
    time you printed → print one short block:
    ```
    Working on:
    - <TICKET-ID>: <a few-word friendly name for it>
    - <TICKET-ID>: <...>
    ```
    one bullet per ticket you're actively progressing right now (your own work, and anything you're
    waiting on from a subagent) — then schedule another wakeup for the same interval. Repeat for as
    long as both conditions hold.
  - Either one breaks (the work finished, or the user already sent something) → print nothing extra
    and stop rescheduling; a real reply already covers it.
- This is a status line, never a reason to sit idle on purpose — don't manufacture background work
  just to have something to report.

## Clean up after yourself: disk and machine

The system drive filled to 1.2 MB free on 2026-11-05. Agents had left 27.6 GB of scratch build copies in
`%TEMP%\claude`, and parallel game players and builds had grown the pagefile to 43 GB (MAT-T90). So:

- **Delete what you made when the task ends.** That covers scratchpad copies of a repo or build tree
  (`Intermediate/`, `obj/`, `bin/`, `Library/`, `*.pch`, `git archive` snapshots), soak/record output you
  no longer need, and converted media. Keep only what the report links to.
- **One heavy process per machine.** Run one game player, one Unity/Unreal build, or one long soak at a
  time. Check for a running one before you launch, and quit what you started (e.g. the harness `quit`)
  before you report.
- **Respect the threshold.** `orchestrator settings --disk-cleanup-gb <GB>` (M.ORCH-T1449) is the global
  floor. Below it, the orchestrator deletes stale agent-owned temp itself. Before writing anything big,
  check free space and clean your own scratch first if you're near the floor. Never delete user files or
  another live session's outputs; report them instead.

## Commits: one ticket, one story, nothing else

This applies to every commit, whoever makes it (`/commit`, `/allocate`, the orchestrator, a subagent, a
manual `git commit`):

- Every commit names its ticket. The subject line ends with the ticket ID in parentheses,
  e.g. `... (M.ORCH-T56)`. A commit that has no ticket yet gets one *before* it's made: `tickets ticket
  new` prints the new ID. Work the user asked for directly counts as approved, so its ticket can be
  logged `--status closed` when the commit finishes it. Every repo's `commit-msg` hook
  (`shared/hooks/commit-msg`, installed by `install-commit-hooks.ps1`) refuses a commit whose subject
  doesn't end with an ID that exists in the ticket database; merges, reverts and fixup!/squash!
  commits pass. Never bypass it with `--no-verify`.
- **Commit by path: `git commit -m "<subject>" -- <path> <path> ...`.** Checkouts are shared (the GOLDEN RULE:
  no separate worktrees), so the index may already hold another agent's staged files; a bare `git commit` takes
  them too. Naming the paths after `--` commits exactly those files, whatever else is staged (`git add` only new
  files first). Never `git add -A`/`git add .`, `git stash`, `git reset` or `git checkout --` in a shared checkout.
- A commit holds the work of one ticket (and the story it belongs to) and nothing else. Two
  tickets or stories mean two commits. Stage by explicit path, and split a file that holds hunks
  for different tickets (stage only that ticket's hunks). Leave anything that belongs to another
  ticket, or to no ticket of yours, unstaged.
- The ticket database and its generated `docs/USER_STORIES.md` are the only shared files that may
  ride along, and only for the ticket being committed.
- Close only the ticket your session claimed. Never close, commit, stage, unstage, revert or reformat another
  agent's work.

**Enforced: the commit gate (M.ORCH-T1530).** `shared/hooks/commit-gate.py` runs in two places:

- **As a CLI hook** (wired by `install-hooks.ps1`): it records which agent (session plus subagent id) modified which
  path and for which ticket. Edit, Write, MultiEdit and NotebookEdit record their file. A shell call records the dirty
  files whose mtime falls inside its run. It learns an agent's ticket from `tickets ticket working|close <ID>` and from
  `git commit ... (<ID>)`, which it trusts, then from the Agent prompt that spawned it, then from
  `tickets ticket show|note <ID>`. It warns, but doesn't refuse, before an edit to a file another live ticket is
  mid-work in. It **refuses `tickets ticket close <ID>`** from a session that doesn't hold the claim (`ticket_work`).
  It also refuses a close while another live subagent works that ticket and this one works a different one. A ticket
  nobody claimed (manual work) closes freely.
- **In git's `commit-msg` hook** (`shared/hooks/commit-msg`, after the ticket-ID check): it sees exactly the paths
  being committed. It **refuses a commit that carries uncommitted changes another agent made for a different, live
  ticket**, meaning one still open and either claimed or worked by an agent seen in the last 3 hours. It **refuses a
  bare `git commit` or `git commit -a`** that would take another live session's modified files, whatever their ticket.
  It warns on a bare commit while other agents are live in the checkout. It warns loudly on a committed file that still
  has unstaged hunks another agent touched. The refusal names the files, the other ticket, its session and its subagent.
- **Overrides.** Put `MINDATTIC_SHARED_OK=<path>[,<path>]` (or `=all`) in front of the commit for a genuinely shared
  file both tickets need. `shared/hooks/commit-gate-shared.json`, plus a repo's own `.agent/commit-gate-shared.json`,
  lists files that always pass: `docs/USER_STORIES.md`, the ticket and orchestrator databases, and generated
  `.agent/commands`. Put `MINDATTIC_FORCE_CLOSE=1` in front of `tickets ticket close`, but only when the user told you
  to close that ticket. `MINDATTIC_COMMIT_GATE=off` turns the gate off. Use the overrides only for those cases, never
  to get past a refusal you don't understand.
- **It fails open.** Any error allows the call or the commit. With no other live agent in the checkout it refuses
  nothing, so a solo user is never blocked. Its state lives in `~/.claude/session-context/commit-gate/`.

Never copy a command's body into a provider-specific or per-project folder. A client-specific
alias (e.g. a non-Claude provider's own command file) must invoke the shared global command or the
runner — never reimplement it.

## Artifacts: every one also lives in the repo (HOUSE-LAW-12)

A Claude artifact lives on claude.ai and has been observed going missing, so the repo copy is the
durable one. This applies to every artifact published or updated while working on a MindAttic
project, not just ones the user asks to save:

1. **Get the full content.** After publishing or updating, read it back
   (`Artifact action: read`, `page: true`) so you have the exact bytes the host now serves —
   never retype or paraphrase it. A multi-file artifact's other published files
   (`action: read`, `path`/`paths`) get inlined into the one HTML file (styles and scripts
   inline, images as data URIs) — a Google Fonts `<link>` is the one exception and stays a link.
2. **Name it from its `<title>`.** Sanitize for the filesystem (strip `< > : " / \ | ? *` and
   control characters, collapse whitespace) and add `.html`. Never name it after the artifact's
   id or URL slug.
3. **Place it.** `<repo>/artifacts/<Title>.html` in the one MindAttic project repo the artifact
   is for. An artifact that isn't about any single project (a general reference page, a tool
   demo) goes in the workspace-root `artifacts/` folder instead. If the repo's `artifacts/`
   folder is already used for something else (e.g. GridGameCaravan's `tools/labcheck.py`
   screenshots), the HTML file sits alongside it — same folder, no collision, since the filename
   comes from the title.
4. **Commit it with the ticket for the work that produced it.** New work and its artifact are one
   story, one commit. A backfill of an artifact from earlier work gets its own `chore` ticket
   (`tickets ticket new --repo <name> --type chore --summary "..."`) in that artifact's repo —
   root-level artifacts (and other workspace-root-only chores) use `--repo MindAttic.Agency`,
   the established home for org-wide tickets, per MAT-T4/MAT-T5.

See `MindAttic.HouseRules.md` HOUSE-LAW-12 for the one-paragraph version every project's
`docs/BIBLE.md` can cite by reference.

## Docs site: every repo on GitHub Pages (HOUSE-LAW-14)

A repo's docs are published by MindAttic.Agency's shared pipeline, never by a per-repo renderer.

1. **Preview locally** (needs `dotnet tool install -g docfx`):
   `powershell -File MindAttic.Agency/shared/docs-site/build-docs-site.ps1 -Root <repo> [-Api] -Serve`.
   It stages README.md as `index.md` plus `docs/**/*.md` in a temp folder, generates `toc.yml` and
   `docfx.json` there, and runs DocFX. Nothing is written into the repo.
2. **Adopt**: `powershell -File MindAttic.Agency/shared/docs-site/adopt-docs-site.ps1 -Repo <name> [-Api] [-RunsOn windows-latest]`.
   It writes `.github/workflows/docs.yml`, deletes `tools/build-readme.ps1`/`.js` and `README.htm`,
   turns Pages on (`build_type=workflow`), sets an empty repo homepage to the site URL, and lists
   any file that still mentions the old renderer. Use `-Api` for any repo with C# code: the API
   reference is read from the `.cs` sources without a NuGet restore (packages in `C:\LocalNuGet`
   aren't in CI), so it works for libraries, apps, GTFO mods and Unity games alike; external types
   just show by name.
3. **Commit** the result with the repo's own docs ticket, push, and check that the `docs` run is
   green and `https://mindattic.github.io/<Repo>/` loads.

Links are rewritten while staging: links between published pages stay page links, images are
copied in, anything else in the repo links to it on GitHub, and links that leave the repo keep
only their text. BIBLE-style `{#id}` anchors and codex front matter are handled too.

**This pipeline is the cross-CLI equivalent for "I need to produce something shareable" (MAT-T103).**
It is plain PowerShell + `git` + the `gh` CLI + GitHub Actions — nothing Claude-specific — so any CLI
can run it. It replaces Claude's `Artifact` tool for the subset that's actually about publishing a
page: a static, version-controlled page anyone can view at `https://mindattic.github.io/<Repo>/`,
rebuilt on every push to `main`. It does **not** replace Artifact's live/interactive runtime
capabilities (a page reading live data, `ArtifactData`'s shared mutable state, the page asking Claude
a question, per-viewer memory, camera/mic/location access, and the rest of the
`artifact-capabilities` roster), in-chat preview/iteration, or claude.ai's own commenting/sharing
surface — see **docs/claude-only-abilities.md** for the full, precise breakdown of what's covered
and what isn't.
